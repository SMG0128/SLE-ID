# H3863 Detector A/B 双板烧录与测试指南

## 1. 本次能验证什么

使用两块小熊派 H3863：

```text
串口命令模拟卡片/测距 -> Detector A --真实 SLE--> Detector B -> GPIO10 动作
                                      <--决策回执--
```

本版本能验证：

- A 端通行状态机是否只在正确顺序通过时生成事件；
- A/B 是否能通过真实 SLE 自动发现、连接和双向通信；
- B 端策略、管理员确认、告警和执行器逻辑；
- 消息 CRC、分片解析和事件去重等公共逻辑。

本版本暂未验证真实卡片、真实 Channel Sounding 测距和第三节点。这些不能靠 DevEco 模拟器准确替代。

## 2. 准备

- 两块小熊派 H3863，分别标记为 A、B；
- 两根可传输数据的 USB 线；
- HiSpark Studio（或你当前能给 H3863 加载 `.fwpkg` 的 DevEco 工具）；
- 两个串口终端，参数为 `115200, 8N1, 无流控`；
- 可选：万用表，或一个 LED 与 330 Ω 左右的串联电阻，用来观察 B 端 GPIO10。

固件：

- A：`outputs/detector_a_h3863_all.fwpkg`
- B：`outputs/detector_b_h3863_all.fwpkg`

## 3. 烧录

为避免选错 COM 口，建议烧录时一次只连接一块板。

### 3.1 烧录 Detector B

1. 只连接准备作为 B 的开发板。
2. 打开 HiSpark Studio 的“程序加载”。
3. 选择 `outputs/detector_b_h3863_all.fwpkg`。
4. 选择该板对应的 COM 口并开始加载。
5. 以工具显示加载成功为准，然后断开 B。

### 3.2 烧录 Detector A

1. 只连接准备作为 A 的开发板。
2. 在“程序加载”中选择 `outputs/detector_a_h3863_all.fwpkg`。
3. 选择 A 板 COM 口并加载。
4. 加载成功后保留 A/B 标记，避免混淆。

注意：A、B 的 SDK 原始输出文件名都是 `ws63-liteos-app_all.fwpkg`，本工程已经将它们分别保存，不能互相替换。

## 4. 串口和 GPIO

应用命令串口配置为：

| 项目 | 值 |
| --- | --- |
| UART | UART0 |
| TX | GPIO17 |
| RX | GPIO18 |
| 波特率 | 115200 |
| 格式 | 8N1，无流控 |
| 行结束 | LF 或 CRLF |

BearPi-Pico H3863 的板载 Type-C/CH340 已连接内部 UART0，直接使用对应 COM 口即可。UART0 使用的 GPIO17/18 是板内连接，并没有作为同名排针引出；排针物理编号 17、18 是 NC，不能在那里接 USB 转串口。板上可外接的是 UART1：物理第 9 脚 UART1_TX/GPIO15、第 10 脚 UART1_RX/GPIO16，但当前固件没有把命令终端配置到 UART1。

B 的执行器输出为 GPIO10（排针物理第 34 脚）：策略允许执行时输出高电平约 500 ms。接外部 LED 时可采用 `GPIO10 -> 330 Ω 电阻 -> LED -> GND`。不要将 5 V 直接接入 GPIO。之所以不使用 GPIO2，是因为当前 SDK 主应用自带的 `led_test.c` 会持续切换 GPIO2。

## 5. 上电和连接

1. 先给 B 上电并打开 B 的 115200 串口。
2. 再给 A 上电并打开 A 的 115200 串口。
3. 必要时分别按一下 RESET。
4. 等待 SLE Server 广播、A 扫描连接和服务发现完成。

B 应至少出现类似日志：

```text
[B] boot: SLE server, actuator pin=10
[sle uart server] service added, ready for connection
[sle uart server] connected, conn_id=...
[sle uart server] === bridge ready ===
```

A 应至少出现类似日志：

```text
[A] boot: SLE client, simulated card=0xa9000001
[sle uart client] connected, conn_id=...
[sle uart client] service discovery complete
[sle uart client] === bridge ready ===
```

只有双方已经出现连接和 bridge ready 日志后再执行测试。

## 6. 基础状态检查

在 A 串口发送：

```text
status
```

在 B 串口发送：

```text
status
```

命令必须以回车或换行结束。若只看到输入字符但没有 `[A]` 或 `[B]` 输出，优先检查串口号、波特率、GPIO17/18 和共地。

## 7. 测试用例

相邻两次 `demo` 之间至少等待 1.5 秒，因为 A 有通行事件冷却时间。

> 安全版固件不再信任 A 串口设置的模拟认证状态。`auth ok/deny/key/replay` 只用于观察 A 的本地状态和未授权事件分支，B 会把没有 HMAC 会话绑定的事件统一视为未授权。只使用 A/B 两块板仍可验证连接、状态机、ACK、重传、去重和拒绝策略；GPIO 执行与管理员确认必须按三端 HMAC 指南加入 Card 后验证。

烧录并出现 `bridge ready` 后，可关闭 VS Code 的两个串口监视器，用脚本自动识别 A/B 并执行用例 1：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File .\tools\ab_security_smoke.ps1 -Port1 COM3 -Port2 COM4
```

成功标志为 `PASS: unbound local authorization was rejected and GPIO stayed off.`。端口号按设备管理器实际结果替换；串口被监视器占用时脚本会明确报错。

### 用例 1：未绑定的本地授权必须被拒绝

B 输入：

```text
policy execute
```

A 输入：

```text
auth ok
demo enter
```

预期：

- A 的三个模拟观测按“接近 -> 第一区域 -> 第二区域”推进；
- B 收到一个事件；
- GPIO10 不动作；
- B 日志包含 `auth=0 action=4 exec=0 reason=1`；
- A 收到相同事件的决策回执。

典型日志：

```text
[B] EVENT event=1 card=a9000001 auth=0 action=4 confirm=0 exec=0 reason=1
[A] decision event=1 action=4 confirm=0 exec=0 reason=1
```

### 用例 2：反向经过应取消

等待 1.5 秒后，在 A 输入：

```text
demo reverse
```

预期 A 出现 `result=2`（取消），B 不应新增 `EVENT`，GPIO10 不动作。可在测试前后对比 B 的 `status` 中 `rx` 计数。

### 用例 3：区域内超时应取消

等待 1.5 秒后，在 A 输入：

```text
demo timeout
```

命令内部会等待约 2.7 秒。预期 A 最后出现 `result=2`，B 不新增事件。

### 用例 4：管理员确认与执行

该项必须先完成 Card HMAC 认证，不能再用 `auth ok` 代替。按 `H3863_THREE_PARTY_AUTH_SERIAL_BRIDGE_TEST.md` 完成三端基础执行后，再把 B 策略设为 `policy confirm` 做人工确认专项测试。

### 用例 5：本地密钥失败模拟不能冒充权威结果

B 输入：

```text
policy execute
```

等待冷却结束后，A 输入：

```text
auth key
demo enter
```

预期 B 不执行 GPIO10。由于事件没有可消费的 B 认证会话，B 统一返回：

```text
auth=0 action=4 exec=0 reason=1
```

### 用例 6：本地重放模拟不能冒充权威结果

等待冷却结束后，A 输入：

```text
auth replay
demo enter
```

预期 B 不执行 GPIO10，并统一返回未授权：

```text
auth=0 action=4 exec=0 reason=1
```

## 9. Protocol V2 升级后的验收点

烧录新版 A/B 固件后，两端启动日志都应包含 `protocol=2`，并显示非零的 `source` 和 `boot`。执行一次 `demo enter` 后：

- A 的 `status` 中 `sent=1`、`ack=1`、`pending=0`；
- B 的 `status` 中 `rx=1`、`dup=0`，且只出现一次执行器 ON/OFF；
- 正常链路下 `retry=0`、`ack_fail=0`、`decision_fail=0`；
- `boot` 每次复位应变化；这是事件键在 A 重启后仍保持唯一的前提。

重试与丢包需要在调试固件或主机故障注入测试中验证；不要通过快速拔电制造串口或 Flash 损坏。主机测试已覆盖首次 ACK 丢失、同一事件重发 1 次且 B 不重复驱动 GPIO，以及连续 4 次发送失败后停止重试。

Detector B：

```text
policy record
policy execute
policy confirm
confirm yes
confirm no
online on
online off
status
```

## 9. 常见问题

### A 一直连接不上 B

- 确认 B 先上电并已出现 Server 广播日志；
- 确认没有把 A/B 固件烧反；
- 两块板先靠近放置；
- 分别复位，仍失败时先断电重启 B，再重启 A；
- DevEco 的软件模拟不能替代这一步真实 SLE 链路测试。

### A 显示 `sent=0 fail` 增加

A 尚未完成 SLE 连接或服务发现。等到 `bridge ready` 后，再等待 1.5 秒并重新执行 `demo enter`。

### B 收到事件但 GPIO10 没有可见变化

- 确认策略为 `policy execute`；
- 确认已完成 Card HMAC 认证且该授权尚未被其他事件消费；仅输入 `auth ok` 不会授权；
- 用万用表测 GPIO10（排针物理第 34 脚）；
- GPIO10 只有约 500 ms 高电平脉冲。

### 连续测试没有新事件

A 有 1.5 秒冷却去重。每次 `demo` 后等待至少 1.5 秒。

## 10. 验收标准

以下条件全部满足即可判定本阶段硬件端 A/B 框架搭建成功：

- 两块板能自动建立 SLE 连接；
- 正向通过只生成一次事件并收到决策回执；
- 反向和超时不向 B 生成完整事件；
- A/B 双板的拒绝、ACK、重传和去重结果符合预期；
- 三端 HMAC 测试中，B 的 GPIO10 在授权允许执行时产生约 500 ms 动作脉冲；
- `status` 中 CRC 错误保持为 0，正常测试没有异常的发送失败。
